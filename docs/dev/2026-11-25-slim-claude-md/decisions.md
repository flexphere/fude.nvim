## D-001 詳細は消さずに docs/architecture/ へ移し、CLAUDE.md は要約にする

- 段階: ヒアリング

  2. 要約のみ（詳細は削除） — 保守が最も軽いが「なぜ」の情報を失う

- 理由: 情報を保ったままコンテキストを減らせる
- 影響: CLAUDE.md、docs/architecture/、ドキュメント更新の規則
- 見直すきっかけ: docs/architecture/ が更新されず古くなっていく、または参照されない
- 関連: AC2, AC3

## D-005 AC6 の対象から develop-v2 を外し、PR #328 の修正はユーザーに委ねる

- 日時: 2026-11-25
- 段階: レビュー
- 重要度: 高（理由: 残る作業がこのブランチの外の PR #328 にあり、受け入れ基準を狭める変更でもある）
- 決めた人: 判断役
- 背景: AC6 は develop-v2 スキルを書き換え対象に挙げたが、develop-v2 は `origin/main` に無く、未マージの PR #328（`docs/develop-v2-skill`）にだけある。レビュー第 1 周で MUST（R1-3）として指摘された
- 選べた案:
  1. PRD から外し、#328 のブランチにこのセッションから push して直す — 別 PR への書き込みに取り決めが無い。マージ順によっては存在しないディレクトリを指す
  2. PRD から外し、#328 には手を出さず報告でユーザーに渡す
  3. #328 のコミットを取り込んでここで直す — 2 つの PR の範囲が混ざる
  4. AC6 を「一部」のまま残す — 満たせない基準が残り続ける
- 決めたこと: 案 2。報告の「見てほしいこと」に #328 の `SKILL.md` 27・133・161 行目と置き換え文面の案を載せる
- 理由: AC6 の前提が事実と合っていなかった。肥大化そのものは check-claude-size が機械的に止め、develop-v2 にも「CLAUDE.md と食い違ったら CLAUDE.md に従う」とあるので、放置した場合の害は限られる
- 影響: PRD の AC6 と変更履歴。#328 は変えていない
- 見直すきっかけ: #328 が先に main に入ったとき（rebase してここで直し、AC6 に戻す）。ユーザーが #328 への push を許したとき
- 関連: AC6, R1-3

## D-006 4 周目は範囲を要約の全称・限定の主張に絞って行い、最終周とする

- 日時: 2026-11-25
- 段階: レビュー
- 重要度: 中（理由: 誤った不変条件は毎セッション読まれ気づかれにくいが、ドキュメントだけで後から直せる）
- 決めた人: 判断役
- 背景: 3 周目でも MUST が 2 件出た（ワークフローでは 3 周後に MUST が残れば判断役が決める）。MUST の推移は 3 → 1 → 2 で、2〜3 周目はすべて「要約が元の記述の限定を落とす」形
- 選べた案:
  1. 全体を新しいレビュー役で MUST 0 まで続ける — AC2・スクリプト・規則は既に安定しており費用に見合わない
  2. 要約と詳細の突き合わせだけに絞った 4 周目を行う
  3. 打ち切り、Copilot と報告に回す — Copilot は要約と詳細の照合に向かず、照合を人に渡すことになる
- 決めたこと: 案 2。4 周目を最終周とする。MUST 0 なら PR へ。同じ形の MUST が 3 件以下なら直して PR へ進み、報告の「見てほしいこと」に挙げる。別の種類の MUST、または同じ形が 4 件以上ならユーザーに判断を仰ぐ
- 理由: 作った側の洗い直しは 2 周目でも 3 周目の指摘を防げておらず、独立の確認が要る
- 影響: レビューの進め方
- 見直すきっかけ: 4 周目で同じ形の MUST が 4 件以上出たとき（要約の書き方の方針を見直す）。マージ後に要約の誤りで実装を誤った例が出たとき
- 関連: AC3, R2-1, R3-1, R3-2

## D-007 報告後の修正 第 2 版: 要約の限定の脱落を全数点検で直す

- 日時: 2026-11-25
- 段階: 報告後の修正 第 2 版
- 重要度: 中（理由: CLAUDE.md の要約全体が対象。ただしドキュメントだけで、PRD は変えない）
- 決めた人: ユーザー
- 背景: 第 1 版の報告で「要約を一度通読してほしい」と依頼したが、ユーザーは通読の代わりに全数点検を求めた。同じ種類の MUST（要約が元の記述の限定を落とし、モジュール全体の決まりのように読める）が 2〜4 周目に続けて出ており、更新後のスキルの「全数点検」に当たる
- 選べた案:
  1. 手直し（PRD は変えない）として全数点検する
  2. 要件の変更として扱う
- 決めたこと: 案 1。要約 36 項目（CLAUDE.md の Module Responsibilities）を 6 区画に分け、点検役を並列に立てて、元の記述（`docs/architecture/`、移動前の CLAUDE.md と同じ本文）と 1 文ずつ照らす。見つかった箇所は実装役に直させ、新しいレビュー役で 1 周して MUST 0 を確かめる
- 理由: 抜き取りのレビューを重ねても、散らばった同じ形の問題は出尽くさない
- 影響: CLAUDE.md の要約、reviews.md、報告ページの「見てほしいこと」
- 見直すきっかけ: 全数点検の後のレビューで同じ種類の MUST が出たとき（区画の取り方か照らし方を見直し、もう 1 回だけ全数点検する）
- 関連: AC3, R2-1, R3-1, R3-2, R4-1〜R4-3
