# lua/fude/gh.lua

Async wrapper around `gh` CLI using `vim.system()`. All GitHub API calls go through `run()`/`run_json()` with callback-based async pattern. Uses `repos/{owner}/{repo}` path templates for REST API (`get_repo_owner(cb, repo?)` — the owner/name the GraphQL queries need — answers from an `owner/repo` slug split by the pure `parse_repo_slug` without running `gh repo view`; `get_review_threads` and `get_pr_viewed_files` take that slug as an optional trailing argument, which every review-session caller fills from `drafts.repo_slug(state.pr_url)`, so a review start no longer spends two `gh repo view` round trips) (resolved by `gh` automatically; every REST listing passes `--paginate` — files, comments, commits, reviews, review comments, issue comments, collaborators — except `get_repo_issues`, whose completion candidates are deliberately capped at `per_page=100`, and `get_pr_by_commit`, where one commit never has 30+ PRs; the default page is 30 items and e.g. `pulls/{pr}/reviews` lists oldest first, so the viewer's pending review on a long-reviewed PR would otherwise never be found) and `gh api graphql` for GraphQL API (used by viewed file management and review thread info: `get_review_threads` returns a `thread_info_map` with per-thread `is_outdated`/`is_resolved` flags plus a comment→thread node ID map; `set_review_thread_resolved(thread_id, resolved, cb)` runs the `resolveReviewThread`/`unresolveReviewThread` mutation built by the pure `build_resolve_thread_mutation(resolved)`). Supports stdin for JSON payloads (used by `create_review()`). `build_changed_files(files)` (pure) converts a `pulls/{pr}/files` / `commits/{sha}` file listing to the `changed_files` entries `{ path, previous_path?, status, additions, deletions, patch }` — `previous_path` comes from `previous_filename` (string only, JSON null ignored) and is used by `preview.lua` to read a renamed file's base content; every GitHub-flow writer of `state.changed_files` (`init.lua` start/reload, `scope.lua` full PR/commit scope) goes through it. `get_pr_info` returns `baseRefOid` (the PR's base commit; `parse_pr_from_commit_api` maps `base.sha` to it) and `title` (stored as `state.pr_title` for the side panel's copy picker, refreshed when the overview data is cached and after a successful `pr.edit` of the reviewed PR) besides the base/head branch names. It detects detached HEAD synchronously via `git symbolic-ref` and uses `get_pr_by_commit` (via `commits/{sha}/pulls` API) directly, avoiding `gh pr view` which may hang without a branch. `parse_pr_from_commit_api` converts the commits API response to the standard PR info format. `get_pr_stack(pr_number, cb)` fetches every PR of the PR's GitHub stack in one GraphQL query (`pullRequest.stack.entries(first: 100)`), parsed bottom-first by the pure, type-defensive `parse_pr_stack` (nil when the PR is in no stack); `checkout_pr(pr_number, cb)` wraps `gh pr checkout`. `get_reactions(path, cb)` (`--paginate`), `add_reaction(path, content, cb)` (POST `-f content=`) and `remove_reaction(path, id, cb)` (DELETE, output not parsed since GitHub answers 204) back `reactions.lua`. Overview editors take an optional trailing `repo` (`owner/repo`), turned into the endpoint prefix by the pure `build_repo_api_path(repo)` (`repos/<repo>`, else gh's `repos/{owner}/{repo}` template resolved from the cwd): `get_collaborators(cb, cwd, repo)`, `re_request_review`, `remove_review_request(pr_number, logins, cb)` (`DELETE pulls/{pr}/requested_reviewers`; adding goes through `re_request_review`, the same endpoint's POST), `get_repo_labels(cb)`, `add_labels(pr_number, names, cb)` (`POST issues/{pr}/labels`; both list functions reject an empty list, which would encode as a JSON object) and `remove_label(pr_number, name, cb)` (`DELETE issues/{pr}/labels/<name>`, the name percent-encoded by the pure `build_path_segment` with an explicit ASCII class rather than the locale-dependent `%w`). `get_pr_info(cb, opts?)` asks for `PR_INFO_FIELDS`, plus — with `opts.with_overview`, on a branch — the overview's `PR_OVERVIEW_FIELDS` (union by the pure `merge_json_fields(a, b)`), reporting through its third callback argument `has_overview` whether the result carries the body (never on a detached HEAD, whose commit lookup returns only the PR info). `get_pr_overview(cb, pr_number?)` runs `gh pr view [<number>] --json PR_OVERVIEW_FIELDS` for the overview (the number is passed whenever known) without `statusCheckRollup` and the reviewers, so the body arrives first; `get_pr_reviewers(pr_number, cb)` (`--json reviewRequests,latestReviews`, nulls → `{}`) and `get_pr_checks(pr_number, cb)` (`--json statusCheckRollup`, JSON null → `{}`) fetch them on their own. `get_reviews` joins a listing of the same PR and cwd still in flight (module-local `reviews_in_flight`) instead of requesting it again, since a review start asks for it twice at once (pending review detection and the overview's review bodies). `get_pr_state(pr_number, cb)` returns `{ number, state, is_draft, url }` (JSON nulls normalized), `get_pr_edit_info(pr_number, cb)` returns `{ number, url, author, reviewRequests, latestReviews, labels }` for the reviewer / label editor commands (nulls normalized, lists to `{}`), and `set_pr_state(action, pr_number, cb)` runs the gh command from the pure `build_pr_state_args(action, pr_number)` (`ready` → `gh pr ready`, `draft` → `gh pr ready --undo`, `close`, `reopen`); `is_no_pr_error(err)` tells "no PR" — gh's "no pull requests found" for a branch, or `get_pr_by_commit`'s "No PR found for commit" on a detached HEAD — from other lookup failures. `get_pr_state`, `get_pr_edit_info` and `get_pr_title_body` share the module-local `view_pr(pr_number, fields, cb)` (`gh pr view --json <fields>` on the PR picked by the module-local `resolve_pr_number`, which looks the number up from the commit on a detached HEAD so `gh pr view` never runs without a branch; each caller normalizes its own fields' nulls).
