# Comments, drafts, reactions, completion

Module details for `lua/fude/comments.lua`, `comments/data.lua`, `comments/sync.lua`, `comments/pickers.lua`, `drafts.lua`, `reactions.lua`, `completion/init.lua`. (`comments/local_sync.lua` is in `local-review.md`.) Moved verbatim from the former "Module Responsibilities" section of `CLAUDE.md`; update this file when these modules change.

- **`comments.lua`** — Facade module re-exporting `comments/data.lua`, `comments/sync.lua`, and `comments/pickers.lua`. Contains comment navigation (`next_comment`/`prev_comment`), creation (`create_comment`/`suggest_change`), viewing (`view_comments`), reply (`reply_to_comment`), editing (`edit_comment`), deletion (`delete_comment`), and thread resolution (`toggle_resolve(comment_id?)` — the given comment's thread, else the first comment on the current line; local mode toggles the JSONL state via `local_sync.toggle_resolved`, GitHub mode calls `sync.toggle_resolved` after refusing a thread whose root is in the user's pending review — `is_pending_comment`, or `find_pending_key` for the first sync before `pending_review_id` arrives — which GitHub has not published). Dispatches mutations to `comments/sync.lua` (GitHub) or `comments/local_sync.lua` (local JSONL) by `state.review_mode`. Local create/suggest (module-local `create_local_comment`) uses the same draft wiring as the GitHub flow (prefill, save/discard on close, removal after the comment is saved); since the local save is synchronous, the draft is removed without a snapshot check. In the local commit scope (`local/session.in_commit_scope()`), the module-local `blocked_by_commit_scope` refuses creation, suggest, reply, edit, delete, resolve, the viewer, next/prev navigation and `list_comments` with a WARN (`local_sync.COMMIT_SCOPE_ERROR`), because the buffer shows a checked-out past commit rather than the working tree comments anchor to. In GitHub mode, `create_comment`/`suggest_change` pass a `pick_submit_kind` to the input so `<CR>` asks (via `vim.ui.select` over `build_submit_choices`) whether to add the comment to the pending review or post it as a single comment (`sync.create_single_comment`); the choice is built at `<CR>` time from `sync.has_pending_review()`, and with a pending review only the review choice exists, so no prompt is shown. Also provides ownership helpers: `is_own_comment`, `is_pending_comment`, `find_pending_key`, and `toggle_resolved_visibility()` (flips `config.toggle_show_resolved()` and refreshes extmarks — used by `:FudeReviewToggleResolved`). The toggle only affects inline comment boxes: `comment_map` always keeps resolved comments, so navigation, the comment viewer, the virtualText style, and the comment browser are unaffected. When boxes are hidden, `ui/extmarks.lua` renders the resolved comments with the virtualText EOL indicator instead. `require("fude.comments")` is the public interface.
  - **`comments/data.lua`** — Pure data functions with no state or side effects: `line_from_diff_hunk`, `build_comment_map`, `find_next_comment_line`, `find_prev_comment_line`, `find_comment_by_id`, `get_comment_thread`, `parse_draft_key`, `build_pending_comments_from_review`, `build_review_comment_object`, `build_submit_choices(has_pending_review)` (single/review submit choices, single first; review only while a pending review exists, since GitHub rejects single comments then), `merge_pending_into_comments`, `pending_comments_to_array`, `get_comment_line_range`, `get_multiline_ranges(comments)` (distinct `{ start_line, end_line }` of the multi-line comments in a list; single-line ones skipped), `get_reply_target_id`, `get_comments_at`, `get_comment_lines`, `build_comment_entries`, `build_comment_browser_entries` (one entry per review thread; see Comment browser thread identity below), `merge_draft_entries` (flags existing entries with `has_draft` for matching reply/edit/issue drafts or an unambiguous line range and appends `type="draft"` rows for new line/suggest/issue drafts, then re-sorts by `last_ts`), `build_pr_level_comments(issue_comments, reviews)` (issue comments plus non-PENDING reviews with a non-blank body — or with any body when the state is in `STATES_SHOWN_WITHOUT_BODY` (APPROVED / CHANGES_REQUESTED / DISMISSED), so an approval without a comment is listed while the empty COMMENTED review every standalone review comment creates is not — converted to issue-comment-shaped objects — `created_at` from `submitted_at`, `review_state`, `is_review_summary = true` — merged oldest first with id as the tie-break; type-checks nested fields since they may be JSON null), `find_thread_key(comment_id, comments, thread_map)` (the id `gh.get_review_threads` indexes the comment's thread under: the root, or the earliest reply keyed in `thread_map` when the root was deleted on GitHub), `find_editable_comment(comments, github_user)` (the user's most recent comment in a thread that is not a review summary — the target of the browser's `e`/`d`, since a review body is edited through another endpoint and cannot be deleted), `find_comment_url(comment, pending_review_id, is_local)` → `url|nil, reason` (the comment's `html_url` for the `o` keys; refused for local review comments and for comments of the viewer's pending review, which GitHub has not published). `build_pr_level_comments` also carries a review's `html_url` (`#pullrequestreview-<id>`) onto its review-summary comment so `o` can open it.
  - **`comments/sync.lua`** — GitHub API sync/submit operations: `load_comments`, `sync_pending_review`, `submit_as_review`, `create_single_comment` (immediately published line/range comment on HEAD via `gh.create_comment`/`gh.create_comment_range`; fails early while `has_pending_review()`), `toggle_resolved(comment_id, cb(err, resolved))` (fetches the threads fresh — `state.thread_map` is only kept while a pending review exists and `is_resolved` is absent when `resolved.show` is false — then flips the thread via `gh.set_review_thread_resolved` and refreshes silently so the result message stays visible; `state.resolving_thread` refuses a second toggle until the first one's mutation *and* refresh land, since both would read the same state and send the same mutation, and a later refresh finishing first would be overwritten by the older one; both gh callbacks drop a response that arrives after `reset_state()` before any error branch), `has_pending_review` (true when `pending_review_id` is set or `pending_comments` is non-empty — the latter covers the first `sync_pending_review` round-trip before the ID arrives), `reply_to_comment`, `edit_comment`, `delete_comment`. `load_comments` is the main entry point: it runs the module-local `fetch_comments` with `detect_pending`, which requests the reviews listing (`GET /pulls/{pr}/reviews`, the viewer's pending review), the submitted comments (`GET /pulls/{pr}/comments`) and — when `outdated.show` or `resolved.show` is on — the review threads in parallel, adds the pending review comments (`GET /reviews/{id}/comments`) and, for its `thread_map`, the threads as soon as the listing reports a pending review, and assembles everything once a barrier over the requests in flight settles (one extra count held while starting them, so a mock answering at once cannot finish early); every other refresh (`fetch_comments` without `detect_pending`) uses the same barrier with the pending state already known, converting `position` to `line` via `line_from_diff_hunk` and building both `comment_map` and `pending_comments`. Also fetches review threads via GraphQL (skipped when `outdated.show` and `resolved.show` are both false and no pending review exists) and applies `is_outdated` (root comments only, gated by `outdated.show`) and `is_resolved` (per-thread state, propagated to replies via `in_reply_to_id`, gated by `resolved.show`) to comment objects. `comment_map` always includes resolved comments (the resolved-visibility toggle acts only on inline-box rendering in `ui/extmarks.lua`). Internal `fetch_comments` is used by other functions for refreshing after mutations. `fetch_pr_level_comments(pr_number, cb)` requests `issues/{pr}/comments` and `pulls/{pr}/reviews` in parallel (barrier count derived from the operation list) and hands `data.build_pr_level_comments` the results, treating a failed listing as empty so the other is still shown; used by `overview.lua` and `ui/comment_browser.lua`. Uses lazy `require("fude.ui")` to avoid circular dependencies.
  - **`comments/pickers.lua`** — Entry point for `list_comments`. Delegates to `ui/comment_browser.open()`.
- **`drafts.lua`** — Local on-disk storage for *unsubmitted* comment input ("drafts"), distinct from the in-session GitHub pending review (`state.pending_comments`). Persists to `stdpath("state")/fude/drafts.json` so input can be paused (jump back to the diff) and resumed later, across PR switches and Neovim restarts. Pure functions (no state/IO): `make_draft_key(repo, pr_number, kind, ...)` builds opaque keys (kind = `line`/`suggest`/`issue`/`reply`/`edit`/`review`/`pr_edit`/`pr_create`; `review` is the `:FudeReviewSubmit` body), `build_draft_scope(st)` (the `repo`/`pr_number` namespace for a state table, shared by `current_key`/`file_markers`/`list_drafts`: GitHub mode → repo slug + PR number; local review mode → `"local:" .. worktree_root` + branch, or `"detached:" .. session.id` on a detached HEAD — keyed by branch rather than session id so drafts survive `:FudeReviewStop`, and `local:` keeps the namespace apart from `owner/repo` slugs; nil without a review target), `repo_slug(pr_url)`, `serialize`/`deserialize` (corrupt JSON → `{}`), `prune(drafts, now, retention_days)`. IO/state helpers: `current_key(kind, ...)` (derives the namespace from `config.state` via `build_draft_scope`; nil for `issue`/`review` in local review mode, which has no PR to post to or review to submit), `enabled()` (reads `config.opts.drafts.enabled`), `load`/`save`/`get`/`get_meta`/`set`/`revision`/`remove`/`remove_if_unchanged` (file is the source of truth — no `config.state` field; `set(key, body, meta?)` stores an optional table returned as-is by `get_meta` — callers validate it, since the file may be hand-edited — used by `pr_create` drafts for the base/stack target; `set` with empty body removes, `load` prunes by `config.opts.drafts.retention_days`; `set` stamps each entry with a `rev` that changes on every save, read back by `revision(key)` (body + `saved_at` for entries written before revisions existed); `remove_if_unchanged(key, snapshot)` takes such a revision and guards async submit-success cleanup so a draft re-saved while the request was in flight survives, even one re-saved with the same body), `file_markers(rel_path)` (one load → `{ lines, comment_ids }` used by `ui/extmarks.lua` to render the `draft` indicator: `line`/`suggest` drafts mark their own line, `reply`/`edit` drafts mark the targeted comment's line via the comment map), and `list_drafts()` (one load → array of `{ key, kind, body, saved_at (normalized to ISO), path?, start_line?, end_line?, comment_id? }` for the active PR, used by the comment browser; browser-facing kinds only via the `BROWSER_KINDS` whitelist — `pr_edit`, `pr_create` and `review` are excluded; skips non-string bodies). `M._dir` overrides the storage dir for tests. Wired into comment creation/reply/edit in `comments.lua`, PR-level comments in `overview.lua`, and the `comment_browser` lower pane (prefill on entry navigation via `lower_key_for_entry`, save/discard on close, snapshot-guarded remove on submit success via `remove_if_unchanged`) and list (draft rows + markers via `merge_draft_entries`). Comment input UIs receive `opts.allow_draft`/`initial_lines`/`on_save_draft`/`on_discard_draft` and report the close action (`submit`/`draft`/`discard`/`cancel`). `pr.lua`'s create float persists here too (kind `pr_create`, keyed by common git dir + branch via `pr.build_create_draft_key`; excluded from the browser and markers like `pr_edit`). `pr.lua`'s edit float also persists here (kind `pr_edit`, one entry per repo + PR, title on line 1) — the key is built via `make_draft_key` with the repo slug from the PR url (not `current_key`, which needs an active session); `pr_edit` entries are deliberately absent from the comment browser (excluded by `list_drafts`'s browser-kind whitelist `BROWSER_KINDS`) and from `file_markers` (prefix mismatch).
- **`reactions.lua`** — Comment reactions. Pure: `CONTENTS` (= `ui/format.REACTIONS`, GitHub's eight in web-UI order), `find_reaction_target(comment, ctx, repo_api_path)` → `path|nil, reason` (`<repo>/pulls/comments/<id>/reactions` for a comment with a `path`, else `issues/comments/<id>/reactions`; refused for no comment, local review (`ctx.is_local`), the viewer's pending review comments (`pull_request_review_id == ctx.pending_review_id`), review summaries and a non-numeric id), `build_rollup(list)` (a reactions listing → the REST `reactions` rollup shape), `find_pr_reaction_target(pr_info, ctx, repo_api_path)` (the PR itself: `<repo>/issues/<n>/reactions`; refused in local review and without a numeric number), `find_user_reactions(list, login)` (content → reaction id), `format_reaction_users(logins, limit?)` (`@a, @b, @c +2`, the first `DETAIL_USERS` (3) then `+N`), `format_reaction_detail(count, on, logins)` (`2 · @me, @alice · <Tab>: remove` / `<Tab>: add`, so every row says who reacted and what `<Tab>` does), `build_reaction_users(list)` (content → `find_reaction_users`), `build_reaction_items(counts, mine, users)` (`ui/toggle_picker` items `{ text = "👍 +1", on, value = content, detail }`, the detail re-read from the caller's live `counts` / `users` tables on every render, both refreshed by each re-list). `pick(comment, ctx, on_done)` (ctx from `ui.capture_open_context()`, repo from `drafts.repo_slug(ctx.pr_url)`) and `pick_pr(pr_info, ctx, on_done)` (repo from `pr_info.url`) both run the module-local `open_picker(path, target, on_done)`, which lists the reactions with `gh.get_reactions` and opens `ui/toggle_picker` (title `Reactions` with `confirm_label = "who reacted"`, so `(<Tab> toggle, <CR> who reacted)` is appended; the toggle picker's spinner marks a row while its request is in flight), whose `on_toggle` sends `gh.add_reaction` / `gh.remove_reaction` (the viewer's reaction id; `state.github_user` identifies it), then re-lists — updating `counts` and the viewer's ids in place, replacing `target.reactions` (the comment, or `pr_info`) with the fresh rollup (so `state.comments` and the overview cache follow) — before `done(true)` and `on_done(target)`; a failed add/remove reports `done(false)` so the row's mark comes back. Its `on_confirm` (`<CR>`) runs the module-local `show_people(item)` through `M.show_people(logins, title, on_pick, on_cancel)` — routed by `file_list_mode` (Telescope dropdown / snacks.picker `select` layout with `auto_confirm = false`, so a single user is shown rather than picked / `vim.ui.select` kind `fude_reaction_people`, also when the plugin is missing), `on_pick` for `<CR>` and `on_cancel` once for any other close (Telescope prompt `BufWipeout`, snacks `on_close`), both scheduled; title from the pure `build_people_prompt(text, count)` naming `<CR> copy username, <Esc> back to reactions` over the pure `find_reaction_users(list, content)` of the latest listing (kept current by each re-list); a pick copies the login with `util.copy_to_clipboard`, and a cancel — or a reaction nobody used — reopens the reaction picker with the same items. `+` is bound in the comment viewer (redraws the float in place via a local `rerender`), the comment browser's thread pane (`update_right_panes` when the entry is still shown) and the overview (a comment under the cursor → `pick` + `handle.set_comments`; anywhere else in the left pane and the whole right pane → `pick_pr` + `handle.refresh_left`, which rewrites the left pane from line 0 through the same module-local `rewrite_left(start)` as `set_comments`). `:FudeReviewReact` runs `react_at_cursor()`: a buffer registered with `set_buffer_handler(buf, fn)` (module-local `buffer_handlers`, dropped on `BufWipeout`) runs that function — the comment viewer, the browser's thread pane and both overview panes register the very function their `+` runs, so the command reuses the `open_ctx` and redraw those UIs captured when drawn; any other buffer needs an active session (else WARN) and takes the cursor line's comments (`diff.to_repo_relative` + `comments.get_comments_at`) through the pure `find_line_targets(comments, ctx)` → `comments|nil, reason` (only those `find_reaction_target` accepts; none → `No comments on this line` or the first comment's reason, INFO like `+`), opening `pick` at once for one and asking through `vim.ui.select` (kind `fude_reaction_target`, rows from the pure `format_comment_choice(comment)`: `@login: ` plus the first non-blank body line cut at `CHOICE_BODY_WIDTH`) for several. The PR's own reactions come from `reactionGroups` (in `gh.PR_OVERVIEW_FIELDS`), converted by the pure `ui/format.build_rollup_from_reaction_groups(groups)` (`THUMBS_UP` → `+1`, … via `REACTION_GROUP_CONTENTS`); `format.find_pr_reactions(pr_info)` prefers `pr_info.reactions` once `pick_pr` set it, and `build_overview_left_lines` shows them under the body. The reactions line itself comes from `ui/format.format_reactions(rollup)` (`👍 2  ❤️ 1`, nil without any), appended after each body by `format_comments_for_display`, `format_reply_comments_for_display` and `build_overview_left_lines` (blank line + reactions line in `REACTIONS_HL`, inside the comment's `comment_ranges`).
- **`completion/init.lua`** — Completion source for comment inputs and PR bodies. `is_enabled(buf?)` accepts `b:fude_comment` or a body registered by `attach_pr(buf, { cwd, base?, pr_number? })`; the latter is deliberately not marked as a comment, since `ui.close_comment_ui` would close it. `pr.open_pr_float` registers only the body before setting its Markdown filetype, and `pr.edit` passes the resolved PR number. The module-local per-buffer context and cache are removed on `BufWipeout`. `fetch_mentions` / `fetch_issues` / `fetch_commits` accept an optional request buffer (forwarded by both blink/cmp adapters), so later focus changes do not retarget requests. Mentions/issues use a 5-minute TTL cache, separate for each PR body and shared by comments. PR editing lazily fetches the explicit PR's commits; creation captures HEAD at attachment and asynchronously reads local `base..tip` commits (retries `origin/<base>`, newest 100 when no base). `parse_git_commits(output)`, `build_commit_items(entries)` and `build_issue_items(issues)` (the `#` candidates, by number descending with `sortText` in that order, so the engines list them newest first whatever order `gh.get_repo_issues` — the 100 most recently updated — returned; entries without a numeric `number` skipped, JSON nulls defaulted) are pure helpers. PR-body commit requests coalesce while in flight and cache successful results, including empty lists, for the body's lifetime; failures are retried, and responses after wipe return empty candidates. All PR-body git/gh calls use the captured cwd; `gh.run` / `run_json` take an optional fourth `cwd` argument, forwarded by the collaborators, issues and PR commits wrappers. Comment commit completion still reads only `state.pr_commits`, invalidating its cache when that list changes. `get_context(line_before_cursor)` parses the `@` / `#` / `_` trigger.

## Comment browser thread identity

`comments/data.build_comment_browser_entries` groups review entries by root comment ID
(following `in_reply_to_id`, including a deleted parent's ID), not by path and ending
line. It retains the positional `comment_map` for inline rendering, adds outdated
comments and unpositioned replies belonging to visible threads, and sorts each thread
root-first with chronological replies (numeric IDs break timestamp ties). Each entry
contains that thread's complete `comments`, so `ui/format.format_comment_browser_thread`
renders the entry directly, including sibling replies after root deletion. Browser
reply submission reads the first comment's `in_reply_to_id` (or its own ID) directly,
since an unpositioned reply need not exist in `comment_map`. Ownership,
pending/resolved labels, reply/edit/delete targets and reply/edit draft markers are
thread-specific. Multi-line entries carry `start_line` and display `path:L15-L20`;
`line`/`lnum` remain the ending line for file jumps. `merge_draft_entries` matches
line/suggestion drafts by the full range only when it identifies one entry; ambiguous
ranges get a separate draft row. The shared `build_comment_map` remains line-based.
