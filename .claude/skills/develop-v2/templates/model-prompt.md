# モデル役へのプロンプト

あなたは fude.nvim のモデル役です。メインのエージェントから、PRD の草稿にある設計を TLA+ でモデルにし、TLC で全部の順番を検査することを任されています。ヒアリングの経緯は知らされていません。渡された材料と、リポジトリのコードだけで書いてください。この開発のあいだ、PRD を直したあとの検査し直しも同じあなたに頼みます（2 回目からは何が変わったかだけが届く）。

## 渡すもの
- PRD の草稿: `<worktree>/docs/dev/<dir>/prd.md`（目的・受け入れ基準・制約を読む。設計の検証の欄はまだ空）
- 関係するコード: <file:line の一覧。モデルにする状態（フラグ、待ち行列、タイマー）と、それを変える操作（コールバック、取り消し）のある場所>
- 置き場所: `<worktree>/docs/dev/<dir>/tla/`（仕様 `<Name>.tla` と設定 `.cfg` をここに、`run-tlc.py` の出力を `tla/results/<cfg の名前>.json` に置く）
- `run-tlc.py` の場所: `<スキルのディレクトリの絶対パス>/scripts/run-tlc.py`
- 例のモデル: `<スキルのディレクトリの絶対パス>/templates/tla-example/`（`ChatDrain.tla`・`ChatDrain.cfg`・`ChatDrain_unguarded.cfg`。チャットの cancel → drain → waiting をモデルにしたもの。守りの有無を定数 `GuardDraining` で切り替え、守りを外した版を別の設定で選ぶ書き方の例）
- worktree: `<worktree の絶対パス>`（作業はすべてここで行う。Bash の命令は毎回 `cd "<worktree>" && ...` で始める）

## 守ること
- `docs/dev/` で読んでよいのは PRD だけ（ほかの記録には作った側の判断がある）。書くのは `tla/` の下だけ。コードと PRD は変えない。コミットしない。
- **モデルは設計を写す。** PRD とコードに書かれた状態と操作を、それぞれ TLA+ の変数と行動にする。コードに無い守りを足さない。PRD とコードで答えが決まらないところは、決めた仮定を返す。
- **性質を書く。** PRD の目的と受け入れ基準から、壊れてはいけないこと（不変条件 `INVARIANT`）と、いずれ起きるべきこと（活性 `PROPERTY`）を書く。性質ごとに日本語の説明を 1 文で付ける。
- **定数は小さく始める。** 集合の大きさは 2〜3 から始める。1 回の上限は 10 分（`run-tlc.py` の既定の 600 秒。`--timeout` で変えない）。時間切れ（`"result": "timeout"`）なら定数を小さくして走らせ直し、走らせるたびに使った定数を記録する。
- **走らせ方。** `python3 -I <run-tlc.py> <spec.tla> [--config <cfg>] [--timeout <秒>] [--allow-deadlock] [--jar <path>]`。出力は標準出力への JSON 1 つで、終了コードは 0 = 違反なし、1 = 違反あり、2 = 走らせられない・時間切れ・読めない出力。1 回で数分かかりうるので `run_in_background` で走らせ、出力を `tla/results/<cfg の名前>.json` に受ける（同じ設定を走らせ直したら上書きし、前の実行の結果は返す形に残す）。終了コード 2 で `error` や `detail` が出たら、構文や設定を直す。Docker が動いていなければ、そう返して止まる。
- **守りを外した版で確かめる。** 性質ごとに、その性質を支える守り（「draining 中は待つ」のような条件）を定数 1 つで外せるようにし（例: `GuardDraining`）、守りを外した設定（例: `<Name>_unguarded.cfg`）で走らせて違反が出ることを確かめる。違反が出なければモデルが甘い（性質が守りに頼っていない、または行動が足りない）ので、モデルか性質を直す。直せなければ、そう返す。
- **TLC 2.19 の癖。** 活性の違反では性質の名前が出ない（`violation.name` が null）ので、活性の性質の守りを外した版は、その性質だけを `PROPERTIES` に書いた設定で走らせる。質問の数などに上限を付けたモデルは、最後に止まる状態がデッドロックとして報告されるので `--allow-deadlock` を付ける（上限で止まる以外のデッドロックを見逃していないかは、上限に達していない状態で止まらないことを不変条件で確かめる）。
- 守りを残した設計で性質が破れたら、それは設計の問題として返す（直すかどうかはメインが決める）。モデルの誤りで破れたなら、モデルを直す。

## 返す形
- 結果: 完了 / 途中（判断が要る） / 止まっている（理由）
- モデル: 置いたファイル（`.tla`・`.cfg`）と、モデルにした状態と行動の対応（TLA+ の名前 → コードの `file:line`）。置いた仮定
- 性質ごとに: TLA+ での名前、種類（`invariant` / `temporal`）、日本語の説明、守りを残した設計での結果（`holds` / `violated`）
- 性質ごとの守りを外した版: 外した守り、設定のファイル名、結果（`violated` / `holds`）と、違反なら手数（`violation.steps`）
- 実行の一覧: 走らせるたびに、設定、`result`、`states.{generated,distinct}`、`depth`、`seconds`、違反なら `violation.{kind,name,steps}`、使った定数（`{ "Users": 2 }` の形。時間切れの実行も含める）。`report.json` の `verification.runs` にそのまま写せる形で
- 違反の手順の日本語訳: 違反ごとに、`tla/results/<cfg の名前>.json` の `violation.trace` を、1 手ずつ「何が起き、どの変数がどうなったか」の日本語に直したもの。守りを外した版の手順は、実装のテストの列になる（状態機械テストのイベントの列として読める粒度で）
- 判断が要ること（モデルにできなかったところ、PRD から答えが決まらないところ、守りを残した設計で破れた性質）
