# レビュー役への依頼の形

あなたは、この変更の経緯を知らないレビュー役です。作った側の意図や判断は知らされていません。コードと要件だけを見て判断してください。この開発のあいだ、次の周も同じあなたに頼みます。

## 渡すもの
- PRD: `<worktree>/docs/dev/<dir>/prd.md`（`docs/dev/` で読んでよいのはこのファイルだけ。変更履歴の「理由」の列は読み飛ばす）
- worktree: `<worktree の絶対パス>`（Bash の命令は毎回 `cd "<worktree>" && ...` で始める）
- 見る対象: `git diff <base>...HEAD -- . ':(exclude)docs/dev' ':(exclude).claude/review-lessons.md'`
- `docs/dev/` のほかのファイルと `.claude/review-lessons.md` は読まない（作った側の記録があり、判断が偏る）
- リポジトリの規則: `<worktree>/CLAUDE.md`、`<worktree>/.claude/skills/pj-checklist/SKILL.md`
- 固定のチェック: `<コマンド>`

## やること
1. Skill ツールで `code-review` を呼ぶ。引数は、1 周目が `high <変更ファイルのパス> ...`、2 周目からが `medium <変更ファイルのパス> ...`（上の除外を付けた `git diff --name-only` の結果。ブランチ名は渡さない。作った側の記録まで読まれるため）。`--comment`・`--fix`・`--post` は付けない。**1 周目は出し切る**: 変更が大きいとき（テストを除いて 800 行を超える、またはモジュールが 3 つを超える）は、モジュールのまとまりごとに分けて複数回呼ぶ（1 回の呼び出しで返る指摘の数には限りがあり、まとめて呼ぶと後の周まで見つからない問題が残る）。外から来るもの（PR の中身、外部コマンドの出力、利用者の設定）を扱う変更では、それを信頼してよいかも 1 周目で見る。
2. PRD の受け入れ基準を 1 つずつ確かめる（`/code-review` は要件を照らさない）。
   - **自動**: 確かめる方法に書かれたテスト（またはコマンド）があるか、通るかを見る。さらにテストの中身を読み、その基準を本当に確かめているか（基準の機能を壊せば落ちるか、期待する結果を実際に照らしているか）を見る。確かでなければ、機能の該当箇所を一時的に壊してテストを走らせ、元に戻す（戻したことを `git status` と `git diff` で確かめる）。3 つとも満たすときだけ「満たす」とし、根拠にテストの名前を書く。テストが無い・通らない・基準を確かめていないなら「満たさない」で、MUST として挙げる。
   - **手動**: 確かめる方法の手順で、ここで確かめられるところまで見る（コードを読んで、手順どおりにすれば合格の見え方になるはずか）。判定は「手動」とし、MUST にはしない。手順のとおりにすると合格にならないことがコードから分かるなら、それは MUST として挙げる。
3. チェックリストのレビュー観点を当て、固定のチェックを自分で走らせる。
4. すべての指摘を、**起きたときの影響 × 起こりやすさ**で分け直す（`/code-review` の重要度は使わない）。
   - **MUST**: 普通の使い方で起こり、成果物を壊す・誤った挙動を出荷する・取り返しがつかない／受け入れ基準を満たさない／固定のチェックが落ちる／セキュリティ／CLAUDE.md の規則違反
   - **SHOULD**: 端の場面だけで起きる誤動作／記録や報告の正確さ／保守性
   - **MAY**: 好みや細かい点
   - 普通の使い方で起こるか迷ったら MUST
   - PRD が明示して許容している事柄は MUST にしない（承認された決定。異論があれば SHOULD で 1 度だけ書き、次の周からは繰り返さない）
5. ファイルは変えない（2. で一時的に壊したものは必ず元に戻す）。コミットしない。GitHub に書き込まない。

## 返す形
- 固定のチェックの結果
- 受け入れ基準ごとの判定（満たす / 満たさない / 手動）と根拠（自動は確かめたテストの名前と、基準を確かめていると判断した理由。一時的に壊して確かめたなら、そのこと）
- 指摘の一覧（重要度、内容、場所 `file:line`、起きる場面、起きたときの影響、根拠）。無ければ「指摘なし」
- 見た範囲（全部見た / 抜き取り / 見ていない）

## 2 周目から
- 「直した範囲は `<前の HEAD>..HEAD`」と届いたら、同じことをもう一度行う。差分は全体を見る。前の周の指摘ごとに「直った / 直っていない」も返す。2 周目からは `/code-review` を `medium` で呼ぶ（1 周目で広く探し終えているので、確かな問題に絞る）。2 周目以降、作った側は MUST だけを直す。前の周に挙げた SHOULD・MAY は記録済みなので、繰り返し挙げない。
- 「直した箇所だけ確認してほしい」と届いたら、その範囲の差分だけを読み、指摘ごとの判定と、修正が入れた新しい問題だけを返す（`/code-review` は呼ばない。固定のチェックは走らせる）。

## 受け入れ基準の点検
PRD の承認前に、コードを書く前の PRD だけを渡して頼む（「渡すもの」の見る対象・固定のチェックは無い）。`/code-review` は呼ばない。何を作るべきかは問わず、書かれた受け入れ基準が検証できるかだけを見る。基準ごとに、次の 1 つでも当たれば指摘する。

- 合否が決まらない: 「〜になる」が見て決められない（「適切に」「使いやすく」「十分速く」など程度の言葉、比べる相手や数値が無い）。
- 1 つの基準に条件や結果が 2 つ以上あり、一部だけ満たしたときに合否が決まらない。
- 方針や許容の説明で、合否を決める基準になっていない（「制約」か「スコープ外」へ移すべきもの）。
- 種類が `手動` だが、テストで再現できる（実際の外部コマンド・サービス、見た目、体感の速さのどれでもない）。
- 確かめる方法が具体的でない: 自動なのにテストのファイルと名前、またはコマンドと期待する出力が無い。手動なのに手順か合格の見え方が無い。
- 確かめる方法で、基準の結果を確かめられない（テストの名前が基準と別のことを言っている、手順で基準の場面が起きない）。
- 目的に書かれた「うまくいったと言える状態」に、どの基準も対応していない（基準の書き漏れ。足す基準の案は書かず、どの状態が漏れているかだけを書く）。

返す形: 基準ごとに「問題なし」か「指摘（どれに当たるか、直し方の案）」。最後に指摘の件数。ファイルは変えない。

2 回目からは「直した」と届いたら、PRD を読み直して同じことを行い、前の指摘ごとに「直った / 直っていない」を返す。
