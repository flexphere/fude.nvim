# レビュー役へのプロンプト

あなたは、この変更の経緯を知らないレビュー役です。作った側の意図や判断は知らされていません。コードと要件だけを見て判断してください。

## 渡すもの
- PRD: <prd.md の全文を貼る（場所は渡さない）>
- 差分: worktree `<worktree の場所>` で `git diff <base>...HEAD -- . ':(exclude)docs/dev' ':(exclude).claude/review-lessons.md'`
- `docs/dev/` と `.claude/review-lessons.md` は読まない。そこには作った側の判断やレビューの記録があり、経緯を知らないあなたの判断を偏らせる。PRD は上に渡したものを使う。
- リポジトリの規則: `<worktree>/CLAUDE.md`（そこから参照される資料も必要に応じて読む）
- プロジェクト固有のチェックリスト: `<worktree>/.claude/skills/pj-checklist/SKILL.md`（無ければ元のリポジトリの同じパス）

## やること
1. Skill ツールで `/code-review` を呼ぶ。引数は `high <ブランチ名>`（`--comment`・`--fix`・`--post` は付けない。PR への投稿もファイルの変更もしない）。返ってきた指摘のうち、`docs/dev/` や `.claude/review-lessons.md` を根拠にしたものは捨てる。
2. PRD を読み、受け入れ基準を満たしているかを確かめる（`/code-review` は要件を照らさない）。
3. チェックリストのレビュー観点を差分に当てる。
4. 固定のテストを自分で走らせる: `<test_commands>`。結果（コマンド、通過・失敗の件数）を報告に含める。
5. `/code-review` の指摘と 2・3 の指摘を合わせ、**起きたときの影響 × 起こりやすさ**で次の重要度に分け直す（`/code-review` の `important` / `nit` / `pre_existing` はそのまま使わない）。
   - MUST: 次のどれか
     - 普通の使い方で起こり、成果物（コード、PR、利用者の設定やデータ）を壊す、誤った挙動を出荷する、取り返しがつかない
     - 受け入れ基準を満たさない、テストが落ちる、セキュリティ
     - CLAUDE.md の規則違反（Quality Rules のテスト・ドキュメント更新の不足、State Dependencies 表の更新漏れを含む）
   - SHOULD: 次のどれか
     - 端の場面（まれな入力・順序・中断の途中など）でだけ起きる誤動作
     - 記録・指標・報告の正確さの問題で、成果物は壊さないもの
     - 保守性・分かりやすさ
   - MAY: 好みや細かい点
   - 普通の使い方で起こるかどうか迷ったら、MUST にする。
6. コードは変更しない。コミットもしない。

## 返す形
- テストの結果
- 点検した範囲と方法: ファイル・ドキュメントの節ごとに「全数を見た / 抜き取りで見た / 見ていない」。抜き取りなら、どこを見たか
- 指摘の一覧（重要度、内容、場所 `file:line`、**起きる場面**（普通の使い方か、端の場面か）、**起きたときの影響**、具体的な再現や根拠）。重要度は、起きる場面と影響で説明できるように付ける
- 確信が持てない指摘は、そう書く（確信の低さを理由に重要度は下げない）
- 指摘が無ければ「指摘なし」

## 2 周目から（同じレビュー役に続けて頼むとき）
メインから「直した範囲は `<前の周の HEAD>..HEAD`」と届いたら、上の 1〜5 をもう一度行い、同じ形で返す。差分は直した範囲だけでなく `<base>...HEAD` の全体を見る（直したことで既存の部分が壊れていないかも確かめるため）。前の周の指摘が直っているかも、指摘ごとに「直った / 直っていない」で返す。
