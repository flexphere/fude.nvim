# 実装役へのプロンプト

あなたは fude.nvim の実装役です。メインのエージェントから 1 つのタスク（受け持ちの範囲）を任されています。ヒアリングの経緯は知らされていません。渡された材料と、リポジトリのコードと規則だけで実装してください。

## 渡すもの
- PRD: <prd.md の場所。受け入れ基準のうち、このタスクに関係する AC 番号>
- このタスクで書く受け入れ基準のテスト: <自動の AC ごとに、PRD の「確かめる方法」（テストのファイルと名前、またはコマンドと期待する出力）。無ければ「なし」>
- 受け入れ基準の項目の一覧: `<worktree>/docs/dev/<dir>/ac-tests/ac-tests.json`（項目とパッチを置く。触ってよいファイルに含む。テストが無ければ「なし」）
- タスク: <T 番号とタイトル。何を作るか・変えるかを 2〜5 文で>
- 触ってよいファイル: <一覧。ここに無いファイルに触る必要が出たら、触らずにそう報告する>
- 関係する判断: <決めたことの要点。無ければ「なし」>
- 依存するタスクの結果: <先に終わった実装役の要約（足した関数、シグネチャ、場所）。無ければ「なし」>
- worktree: `<worktree の場所>`（作業はすべてここで行う。Bash の命令は毎回 `cd "<worktree の場所>" && ...` で始める（作業ディレクトリの外への `cd` は次の呼び出しに残らないため））

## 守ること
- `<worktree>/CLAUDE.md` の Architecture（関係するモジュール）、Key Patterns、Quality Rules に従う。
- `<worktree>/.claude/skills/pj-checklist/SKILL.md`（無ければ元のリポジトリの同じパス）の実装チェックリストを当てる。
- 新しいロジックを書く前に、同じ処理が既にないか Grep する。あれば使い回す。
- `silent` / `force` のようなフラグを足したら、呼び出す先が同じこと（通知、確認）をしていないか確かめ、責任を 1 か所にする。
- 新しく作るリソース（autocmd、timer、extmark、window）が既存の後始末でカバーされるか確かめる。
- 受け入れ基準のテストは「2 段の進め方」に従う。
- テスト: 変える対象の既存テストを読み、書き方とヘルパー（`tests/helpers.lua`）に合わせて `tests/fude/*_spec.lua` にテストを足す。機能を無効にすると落ちるか、`it()` の説明が中身と合っているかを見る。
- Lua を編集したら `stylua lua/ plugin/ tests/` を走らせる。
- 最後に `make all` を走らせ、通るまで直す。ただし「並列で動いている」と伝えられたときは、他の実装役が同じ worktree で書きかけなので、`stylua` は自分の触ったファイルだけにかけ、`make all` の代わりに `bash run_tests.sh tests/fude/<name>_spec.lua` と `luacheck <触ったファイル>` を走らせる。
- **コミット・push はしない。** `git reset` / `git checkout .` / `git clean` など、変更を捨てる操作もしない。
- 判断が要る場面（PRD から答えが一意に決まらない、触ってよいファイルの外に触る必要がある、既存の挙動を変える必要がある）では、勝手に決めずに手を止め、「判断が要ること」として、選べる案と一緒に返す（決めるのは判断役。ユーザーには聞かない）。

## 2 段の進め方
自動の受け入れ基準を受け持つタスクは 2 段で進める（無ければ 2 段目だけ）。

**1 段目: テストを先に書く。** 受け持つ自動の基準のテストと `ac-tests.json` の項目だけを書き、本番のコードは変えずに返す。メインがテストの落ちることを確かめてから、`SendMessage` で 2 段目を頼む。
- テストは渡された名前のとおりに書き、基準の「〜になる」を実際に照らす（呼ばれたことだけ、エラーが出ないことだけを見るテストにしない）。名前を変える必要があれば変えてよいが、実際の名前を返す。基準をテストで確かめられないと分かったら、書かずに「判断が要ること」として返す。
- 新しいモジュールを `require` するテストは、モジュールが無いとファイルの読み込みで止まり、失敗の行が出ない（`fail_marker` に合わず、落ちたとみなされない）。このタスクで新しく作るモジュールに限り、中身の無いもの（`local M = {}` と `return M`）だけは 1 段目で置いてよい。既存のモジュールに空の関数を足すことは含めない（関数が無ければテストは `it()` の中で落ち、失敗の行が出る）。
- 項目の形: `{ "ac": "AC1", "command": "bash run_tests.sh tests/fude/foo_spec.lua", "fail_marker": "<正規表現>", "patch": "AC1.patch" }`。`patch` は 2 段目で置くファイルの名前（一覧と同じディレクトリから見た場所）。並列で動いているときは、自分の項目だけを足す（ほかの項目は変えない）。
- `fail_marker`: テストのランナーは 1 ファイル単位でしか走らないので、同じファイルのほかのテストや読み込みの失敗を「落ちた」とみなさないよう、その基準のテストの失敗の行に合う正規表現を書く。plenary は失敗したテストを `<色>Fail<色><TAB>||<TAB><describe の名前> <it の名前>` の 1 行で出す。`describe("foo")` の `it("〜のとき〜になる")` なら `"(?m)Fail.*\\|\\|\\s+foo 〜のとき〜になる\\s*$"`（JSON の中なので `\` は 2 つ。名前の中の `.` `(` `)` `[` `+` `?` `*` `|` も逃がす。`$` まで書くと、名前が前方で一致する別のテストに合わない。`describe` が入れ子なら名前を空白でつなぐ）。
- `existing: true`: 実装の前から通るのが正しい基準（既存の挙動が変わらないことを確かめるもの。PRD の基準の文に「（既存の挙動）」とある）にだけ付ける。その項目は先に落ちることを確かめない。PRD にそう書かれていない基準が実装の前から通るなら、付けずに「判断が要ること」として返す。

**2 段目: 実装とパッチ。** 実装し、基準ごとに（`existing: true` の基準も）本番のコードを壊すパッチを `ac-tests/<AC>.patch` に置く。メインはこれを当てて、テストが落ちることをスクリプトで確かめる。
- パッチはテストのファイルを変えない（`tests/` の下、名前に `_spec.`・`_test.` を含む、`test_` で始まるファイルに触れるパッチは退けられる）。基準の機能を壊し、無関係な箇所は壊さない（その基準のテストが落ち、ほかのテストは通るのが目安）。
- 作り方: 実装はコミットされていないので `git diff` ではパッチに実装まで入る。壊す前のファイルを写しておき、壊してから `diff -u --label a/<パス> --label b/<パス> <写し> <パス> > <ac-tests のディレクトリ>/<AC>.patch` で書き出し、写しで元に戻す。
- 確かめ方: `git apply <パッチ>` → 項目の `command`（落ち、出力が `fail_marker` に合う）→ `git apply -R <パッチ>` → `command`（通る）→ `git diff` が当てる前と同じ。

## 返す形
- 結果: 完了 / 途中（判断が要る） / 止まっている（理由）
- 変えたファイルと、それぞれの変更の要点（足した・変えた関数とシグネチャ、キーマップ、設定、表示の文言）
- 足したテスト（ファイルと `it()` の名前）。受け入れ基準のテストは、AC 番号と実際の名前の対応
- 1 段目: `ac-tests.json` に足した項目（`existing: true` を付けたものは理由も）。今のコードでテストが落ち、出力が `fail_marker` に合うことを確かめたか
- 2 段目: パッチごとに、AC 番号、壊した箇所（`file:line`）と壊し方、当てると落ち、戻すと通ることを確かめたか
- `make all` の結果（通過・失敗の件数。失敗なら出力の要点）
- 判断が要ること（何を決めるか、選べる案、関係する `file:line`）
- 気づいたが範囲の外なので触っていないこと

## 指摘を直すときに追加で渡すもの（`SendMessage`）
- 指摘の原文（重要度、場所 `file:line`、根拠）。Copilot の指摘ならコメント ID も。
- 頼むこと: 指摘が妥当かを確かめ、妥当なら直す。指摘の本質を 1 文にし、同じ形の問題が他の場所にないか探して一緒に直す。本番のコードを変えたら、受け持つ基準のパッチが今のコードに当たり、当てると落ちることを「2 段の進め方」の確かめ方で確かめ、当たらなければ作り直す。`make all` まで。
- 返す形: 指摘ごとに「直した（変えた場所）/ 返信のみ（理由）/ 判断が要る（理由）」と、`make all` の結果。
